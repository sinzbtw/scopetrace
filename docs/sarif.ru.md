# SARIF 2.1.0 и GitHub Code Scanning

ScopeTrace 0.4.0 экспортирует SARIF 2.1.0 для github-oauth, github-app и google-oauth. Экспорт выполняется локально без сети. Загрузка на GitHub — отдельный явный шаг workflow.

## Экспорт

Запускайте из корня приложения:

~~~sh
scopetrace scan --format sarif --output report.sarif
scopetrace scan --config config/permissions.json --format sarif --output gated.sarif --fail-on high
~~~

Без --output stdout содержит только SARIF JSON. Существующий файл не перезаписывается. При срабатывании порога полный отчёт сохраняется до выхода с кодом 1; ошибка выполнения/конфигурации возвращает 2, и устаревший отчёт загружать нельзя. Gate по-прежнему учитывает только insufficient со средней/высокой уверенностью. Формат не меняет анализ и версии JSON-схем провайдеров 1.0.0/2.0.0/3.0.0.

Программный API: toSarif(report, { configFile: 'config/permissions.json' }) возвращает объект; render(report, 'sarif', options) — строку. Для нестандартной конфигурации передавайте её фактический относительный путь. CLI делает это автоматически, в том числе для абсолютного --config внутри корня проекта.

## Находки и уверенность

| Категория ScopeTrace | SARIF |
| --- | --- |
| insufficient | error для high, warning для medium, note для low/info |
| possibly_excessive | note с низкой уверенностью, рекомендация для ревью |
| unknown | note с исходной уверенностью и объяснением неопределённости |
| observed / not_applicable | Сохранены в run.properties.scopetrace.nonAlertFindings без создания alerts |

Каждый результат хранит confidence, category и исходную severity в properties и видимом сообщении. В properties.scopetrace остаётся вся структурированная находка: правило каталога, альтернативы, доказательства, ссылки, read/write-уровни GitHub Apps и Google sensitivity/предложения scopes. Метаданные запуска сохраняют ограничения, уведомления, операции, объявления прав и категории Google scopes. Unknown-категории не превращаются в non-sensitive.

Идентификаторы SARIF-правил включают провайдера, правило каталога (или declaration), категорию, важность и уверенность. Это не ID отдельной находки. Разные варианты уверенности получают соответствующий GitHub precision, не повышая уверенность других результатов. Численные CVSS/security-severity не выдумываются: это находки для ревью прав, а не доказанные уязвимости.

Для API-операции используется настоящая позиция: файл, строка и UTF-16-столбец, начиная с 1. Относительные пути имеют прямые слеши и URI-кодирование пробелов, #, ?, %, кириллицы и других символов. Абсолютные пути, выход за корень и некорректные позиции отклоняются. Исходники, токены, ID ресурсов, тела/значения query и абсолютный корень проекта не добавляются.

Находки по объявлениям прав и общие уведомления привязываются к фактическому файлу конфигурации целиком, без вымышленной строки. Их можно увидеть в Code Scanning, но это не обещает inline-комментарий на конкретном scope. Неполный обход сохраняется в метаданных и предупреждениях SARIF. Успешный экспорт не доказывает полноту анализа приложения.

Fingerprints учитывают провайдера, относительный путь, нормализованную операцию/объявление и порядковый номер одинакового вызова. Строка/столбец и версия исключены: вставка посторонних строк не меняет все alerts. Перестановка/добавление одинаковых вызовов или смена категории/уверенности может изменить идентичность. Экспорт не перечитывает исходники ради хеширования; upload action может добавить свой fingerprint строки.

## GitHub и Pull Requests

Скопируйте [github-code-scanning.yml](../examples/github-code-scanning.yml) в .github/workflows вашего приложения и сохраните конфигурацию ScopeTrace. Workflow собирает инструмент на проверенном полном SHA, отдельно получает код приложения и загружает отчёт через закреплённый upload-sarif v4. Зависимости/скрипты проверяемого приложения не устанавливаются и не запускаются.

Используются pull_request и push в main, чтобы у основной ветки был baseline. Для PR сохраняются стандартные merge-ref GitHub; не подменяйте checkout посторонней веткой. checkout_path: app сопоставляет пути с корнем проверяемого репозитория. Каждой конфигурации/части монорепозитория нужна отдельная стабильная category. Пути и category должны совпадать между основной веткой и PR. При анализе вложенного корня приложения адаптируйте пути/checkout, чтобы пути оставались относительными к репозиторию.

Код 1 сначала сохраняется, затем выполняется upload и только после него — падение gate. Код 2 сразу останавливает загрузку. Собственная политика Code Scanning в GitHub и локальный --fail-on — независимые проверки.

Права workflow: contents: read и security-events: write; actions: read также поддерживает private-репозитории. pull-requests: write и отдельный токен не нужны, используется GITHUB_TOKEN. Fork/Dependabot PR запускаются через pull_request с предусмотренной GitHub поддержкой загрузки при ограниченном токене; применяются настройки одобрения и Actions репозитория. Не переходите на pull_request_target и не выдавайте личный write-токен для выполнения недоверенного PR-кода.

Code Scanning должен быть доступен и включён в целевом репозитории. Он доступен для публичных репозиториев GitHub.com; private/организационные возможности зависят от тарифа и настроек GitHub Code Security. Workflow не покупает и не активирует платные функции.

Inline-аннотация PR появляется, только если указанная позиция находится в добавленных/изменённых строках diff. Файловая привязка конфигурации, неизменённые строки, исключённые файлы и неподдерживаемые операции не гарантируют inline-аннотаций. Общие результаты смотрите в проверках Code Scanning и вкладке Security. Для больших отчётов учитывайте лимиты GitHub; сужайте include или делите анализ на стабильные категории.

## Проверки и источники

Автономные тесты проверяют все три провайдера по неизменённой официальной схеме OASIS, уверенность, приватность, URI, fingerprints, CLI/gate и контракт workflow. CI проверяет собранный SARIF CLI на Windows/Linux с Node.js 22/24/26. Это не утверждение о live-проверке всех настроек GitHub и условий показа PR-аннотаций.
